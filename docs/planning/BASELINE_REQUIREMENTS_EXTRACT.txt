# ADR-003: Data Persistence and Schema Ownership

## Status
**Accepted**
----------------------------------------
FILE: D:\Documents\fast_courses\3rdsem\intor to SE\assignment_4\docs\baseline\deliverable-3\ADR\ADR-003-data-persistence.md

## Alternatives Considered

----------------------------------------
FILE: D:\Documents\fast_courses\3rdsem\intor to SE\assignment_4\docs\baseline\deliverable-3\ADR\ADR-003-data-persistence.md
| `tranche_scheduling` | `tranches`, `authorization_windows` | Scheduled intervals; mutated by scheduler |
| `trade_execution` | `trade_authorizations`, `executions` | **`executions` is strictly APPEND-ONLY (XC-03)** |
| `watchlist` (TA-Provided) | `watchlist_entries` | User-isolated; no financial table links |
| `investment_journal` (TA-Provided) | `journal_notes` | Private notes; references plan/signal IDs only |

----------------------------------------
FILE: D:\Documents\fast_courses\3rdsem\intor to SE\assignment_4\docs\baseline\deliverable-3\ADR\ADR-003-data-persistence.md
- **Atomic Operations:** Creating an approved plan, setting up 3 tranches, and inserting notification outbox tasks occurs atomically in a single ACID transaction.
- **Immutable Ledger (XC-03):** The `executions` table is append-only. Application repositories forbid `UPDATE` and `DELETE` queries on this table, guaranteeing an incorruptible financial audit trail.
- **Optimistic Locking:** Tables supporting concurrent state changes (`investment_plans`, `tranches`) incorporate a `version_id` column to prevent race conditions during rapid user clicks (e.g., Pause/Resume).

## Trade-offs and Consequences

# ADR-004: Authentication and Trade Authorization Boundary

## Status
**Accepted**
----------------------------------------
FILE: D:\Documents\fast_courses\3rdsem\intor to SE\assignment_4\docs\baseline\deliverable-3\ADR\ADR-004-authentication-authorization.md
- **ASRs:** ASR-01, ASR-02, ASR-06, ASR-08

## Alternatives Considered

----------------------------------------
FILE: D:\Documents\fast_courses\3rdsem\intor to SE\assignment_4\docs\baseline\deliverable-3\ADR\ADR-004-authentication-authorization.md
- **Pros:** Trivial to implement.
- **Cons:** Fatal security flaw. A compromised client or modified HTTP request can fabricate authorizations without human interaction. Fails NFR-02 and C-01.

### Alternative 2: OTP-Per-Tranche Authorization
- **Description:** Server sends an SMS/Email OTP for each individual tranche order.
----------------------------------------
FILE: D:\Documents\fast_courses\3rdsem\intor to SE\assignment_4\docs\baseline\deliverable-3\ADR\ADR-004-authentication-authorization.md
- **Pros:** Server-verifiable without mobile trust complexity.
- **Cons:** Violates Resolved OQ-06 (which mandates native OS biometrics / PIN); OTP is designated strictly for PIN recovery. Fails 60-second window usability.

### Alternative 3: 4-Stage Separation with Device-Signed Ephemeral Order Grant Tokens (Selected)
- **Description:** Establishes a four-stage boundary pipeline:
----------------------------------------
FILE: D:\Documents\fast_courses\3rdsem\intor to SE\assignment_4\docs\baseline\deliverable-3\ADR\ADR-004-authentication-authorization.md
### Authorization Rules:
1. **Server-Side Expiry Enforcement (XC-05):** The 60-second authorization window is anchored to a server-side timestamp (`authorization_expires_at`). Verifications completing at second 61 fail closed and the tranche is permanently skipped.
2. **Pre-Execution Check:** Before order dispatch, the server synchronously validates:
   - Grant token cryptographic validity and expiry ($\le 60\text{s}$).
   - Market data freshness ($<5\text{s}$ latency, $<15\text{s}$ staleness).
----------------------------------------
FILE: D:\Documents\fast_courses\3rdsem\intor to SE\assignment_4\docs\baseline\deliverable-3\ADR\ADR-004-authentication-authorization.md
   - Price shift condition: current price $\le$ entry price $\times 1.02$ (strict $>2.0\%$ triggers lock).
3. **PIN Recovery Isolation:** PIN recovery requires 2FA OTP verification delivered to registered phone/email (Resolved OQ-06).

## Rationale
- **Eliminates Autonomous Execution (XC-02):** Cryptographically impossible for backend schedulers to submit trades without a freshly signed device grant token.
----------------------------------------
FILE: D:\Documents\fast_courses\3rdsem\intor to SE\assignment_4\docs\baseline\deliverable-3\ADR\ADR-004-authentication-authorization.md
## Rationale

## 17. Security Architecture
- **Zero-Trust Credential Vault:** Keys are verified with exchange APIs before storage. Keys with withdrawal permissions are unconditionally rejected (XC-11).
- **Zero-Codebase Withdrawal Guarantee:** The system contains zero withdrawal methods, endpoints, or data models (XC-04).
- **Ephemeral Order Grant Tokens:** Biometric authentication unlocks a device-bound key to sign an ephemeral token (`tranche_id`, `expires_at`). Server validates signature and enforces `now() <= expires_at` before decrypting trading keys.
- **2FA OTP Recovery:** PIN recovery requires two-factor verification sent to registered contact info (Resolved OQ-06).
