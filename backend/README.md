## Description

[Nest](https://github.com/nestjs/nest) framework TypeScript starter repository.

## Project setup

```bash
$ npm install
```

## Compile and run the project

```bash
# development
$ npm run start

# watch mode
$ npm run start:dev

# production mode
$ npm run start:prod
```

## Run tests

```bash
# unit tests
$ npm run test

# e2e tests
$ npm run test:e2e

# test coverage
$ npm run test:cov
```

## Deployment

When you're ready to deploy your NestJS application to production, there are some key steps you can take to ensure it runs as efficiently as possible. Check out the [deployment documentation](https://docs.nestjs.com/deployment) for more information.

If you are looking for a cloud-based platform to deploy your NestJS application, check out [Mau](https://mau.nestjs.com), our official platform for deploying NestJS applications on AWS. Mau makes deployment straightforward and fast, requiring just a few simple steps:

```bash
$ npm install -g @nestjs/mau
$ mau deploy
```

With Mau, you can deploy your application in just a few clicks, allowing you to focus on building features rather than managing infrastructure.

## Observability

In production applications, observability is essential for understanding how your system behaves, detecting issues early, and maintaining reliable performance.

[NestJS Observe](https://observe.nestjs.com) automatically instruments your NestJS application, giving you deep visibility into your system with minimal setup:

- **Distributed tracing:** Follow requests across services and understand how they flow through your system.
- **Waterfall analysis:** Visualize request execution and identify slow operations, bottlenecks, and unexpected delays.
- **Performance analysis:** Analyze application performance in real time and quickly pinpoint areas that need optimization.
- **Metrics:** Track key application and infrastructure metrics to understand system health and performance trends.
- **Logging:** Centralize and correlate logs with traces and other telemetry to make debugging easier.
- **Error tracking:** Detect errors quickly and investigate their root causes with the surrounding context.
- **SLA monitoring:** Track service-level objectives and identify when your application is approaching or exceeding defined thresholds.
- **Alarms and alerts:** Set up alerts for critical errors, performance degradation, SLA violations, and other anomalies so your team can react quickly.

This project is already instrumented. To connect it, run this and approve the code it prints at [observe.nestjs.com/link](https://observe.nestjs.com/link) - signing up for free if you have no account:

```bash
$ npx @nestjs/observe link
```

It writes the app key and secret into `.env` and makes every `nest start` script (`start`, `start:dev`, `start:debug`) load it. In production, set `OBSERVE_APP_KEY` and `OBSERVE_APP_SECRET` in the environment instead.

Or do it by hand: create an application and an API key at [observe.nestjs.com](https://observe.nestjs.com), and set the pair as `OBSERVE_APP_KEY` and `OBSERVE_APP_SECRET` in the environment the app runs in.

The free plan needs no payment details and covers 300,000 events a month. You can also browse the [live demo](https://www.observe-demo.nestjs.com/dashboard) first - the whole dashboard over a busy service's data, with nothing to install.

## ADVISORA local configuration

1. Create a PostgreSQL database named `advisora` (or set `DB_NAME` to your local database).
2. Copy `.env.example` to `.env` and set local database credentials plus a strong random `JWT_SECRET`. Never commit `.env`.
3. Apply migrations in numeric order using `psql` or your PostgreSQL client:

```bash
psql -U postgres -d advisora -f src/database/migrations/001_create_users.sql
psql -U postgres -d advisora -f src/database/migrations/002_auth_sessions_devices.sql
```

4. Install dependencies with `npm ci`, then run `npm run build` and `npm test -- --runInBand`.
5. Start the API with `npm run start:dev`. The default API port is 3000.

### VS-01 authentication endpoints

- `POST /auth/register` and `POST /auth/login` issue a one-hour bearer session.
- `GET /auth/me` requires an active bearer session.
- `POST /auth/logout` revokes the current session server-side.
- `POST /auth/devices/challenge` creates a five-minute one-time Ed25519 registration challenge.
- `POST /auth/devices` registers a device only after proof of private-key possession. The client signs the exact UTF-8 `challenge` string with Ed25519 and sends its base64url signature and PEM public key.
- `POST /auth/devices/:id/authorization-challenge` creates a one-time challenge bound to an active registered device.
- `POST /auth/devices/:id/verify` verifies an Ed25519 signature against that device's stored public key and consumes the challenge exactly once. The response is proof-of-possession verification only; it is not a tranche authorization grant.
- `GET /auth/devices` lists the current user's active devices.
- `DELETE /auth/devices/:id` revokes one of the current user's devices. Revoked devices cannot obtain or complete new verification challenges.

Device registration and device proof-of-possession are not tranche authorization. Native operating-system biometric integration, PIN recovery using two-factor OTP, and the tranche-specific ephemeral grant flow remain separate work under the approved ADR-004 boundary. The server must independently bind any future grant to its specific tranche and enforce the 60-second expiry.
